# dev-brain

个人开发知识库，独立 Git 仓库。三类信息各有唯一真源，不在多处维护不同版本：

- 代码、测试和可执行检查：业务仓库 Git。已有可执行测试就链接它，不在别处另写一份验收标准。
- 任务目标、进度、交接、验证证据和过程产物：dev-brain 中这次任务的任务记录。
- 长期知识结论：dev-brain 正式笔记，只由本机 curator 写。

## 定位库根

库根（下文 `$DEV_BRAIN`）是本 SKILL.md 所在 Git 仓库的根目录。技能目录可能是符号链接，用 Git 解析真实路径：

```bash
git -C <本 SKILL.md 所在目录> rev-parse --show-toplevel
```

解析失败或得到的不是库根时（例如 Windows 上通过目录联接安装）读 `~/.config/dev-brain/vault`，里面是安装时写下的库根绝对路径。shell 变量不跨命令保留，后续命令直接写解析出的绝对路径。

## Windows（PowerShell）

下文命令按 bash 写。在 PowerShell 里 `git`、`rg` 照用，以下几处换写法：

| 用途 | bash | PowerShell |
|---|---|---|
| 按命中数排序 | `… \| sort -t: -k2 -nr \| head -20` | `… \| Sort-Object { [int]($_ -split ':')[-1] } -Descending \| Select-Object -First 20` |
| 入队 handoff | `dev-brain-handoff <<'EOF' … EOF` | `@'` 换行 `…` 换行 `'@ \| & "$DEV_BRAIN\_system\bin\dev-brain-handoff.ps1"`（`'@` 必须顶格） |
| curator | `dev-brain-curator run\|status\|sync` | `& "$DEV_BRAIN\_system\bin\dev-brain-curator.ps1" run\|status\|sync` |
| 查未完成任务 | `rg -l '^- 状态：(…)' <目录>` | 相同；路径用 `\` 或 `/` 都行 |

不要用 `>` 把命令输出写成文件（Windows PowerShell 5.1 会写成 UTF-16）；需要落文件时用命令自带的输出参数，例如 `git diff --output=<文件>`。

## 边界

- 加载本技能只授权检索（含开工时的 fast-forward 拉取）。写任务记录、提交、入队按下文各节的条件进行。
- 不为知识管理修改业务仓库。仓库自己要求的任务文档按仓库规则另写，与 dev-brain 的任务记录互不替代。
- 会话只写三处：自己的任务目录（`projects/<id>/tasks/`）、具体问题的 issue 工作台（`projects/<id>/issues/`，规则见 `_system/rules.md`）、作为项目长期参考的图（`projects/<id>/diagrams/`，见「产物」）。正式笔记、hub、`knowledge/`、`status` 都由 curator 改，会话要沉淀的东西一律写成 handoff。
- 提交只带自己写的路径：`git -C $DEV_BRAIN add -- <路径>`，再 `git -C $DEV_BRAIN commit -m "<前缀>: <一句话>" -- <路径>`；Codex 前缀 `codex:`，Claude 前缀 `claude:`。不用 `add -A`。遇到 `index.lock` 稍等重试，不删锁。推送由 curator 执行器负责（见「同步」）。
- 无源不落库：外部信息带 URL，代码结论带 `仓库名@commit:路径`（commit 取 `git rev-parse --short HEAD`），handoff 也一样。
- 技术结论进 dev-brain，不写进 agent 自带的记忆。

## 什么时候建任务记录

| 工作 | 做法 |
|---|---|
| 小修、文案、低风险局部调整；一问一答 | 必要时快速检索 → 完成 → 回复里给结果，不建任务记录。一问一答里有值得留的结论就发 handoff |
| 明确的功能或缺陷 | 对齐改动思路 → 建记录 → 行为例子 → 适合自动验证的先写失败测试 → 小步实现 → 回归 |
| 模块重构、公共接口、数据所有权变化 | 对齐结构提案（哪里变、为什么、代价），关键取舍由用户定 → 建记录 → 实现 → 审阅测试与结构差异 |
| 调研、梳理、学习、方案讨论 | 对齐范围与做法（查什么、怎么查、产出什么）→ 建记录 → 证据与假设 → 阅读或小实验 → 更新判断；成果写成任务目录里的报告或草稿，交给 curator；明确实现目标后转入开发流程 |
| 具体故障排查 | 用 issue 工作台代替任务记录，不重复建两份；只读排查可先做，改代码前对齐修复思路 |

「对齐」见「动手前对齐」。对齐确认后连续工作，不逐步索取确认；小修和一问一答不需要对齐。

## 开工

1. **拉取**：`git -C $DEV_BRAIN status --porcelain` 无输出时执行 `git -C $DEV_BRAIN pull --ff-only`。不干净或失败就用本地副本，并在回复里说明。
2. **检索**，逐步展开，够用就停：
   - 定项目：在 `$DEV_BRAIN/projects/` 下找与当前仓库或主题对应的目录，读其 `_hub.md` 前 80 行左右（目标、涉及仓库、最近状态）。hub 可能很长，不要整篇读。
   - 标题即主题：`rg --files -g '*.md' $DEV_BRAIN | rg -i -e <词1> -e <词2>`。
   - 正文按命中数排序：`rg -i -c -g '*.md' -e <词1> -e <词2> $DEV_BRAIN | sort -t: -k2 -nr | head -20`；对排前的几篇看片段：`rg -i -n -m 3 -C 1 --max-columns 300 --max-columns-preview -e <词1> -e <词2> <文件…>`。关键词用项目名、模块名、类名、报错原文，中英文各试一组；命中太多就加 `-g 'projects/<id>/**'` 收窄。
   - 只对真正相关的一两篇读全文，看它 frontmatter 的 `status`；需要历史决定或相邻机制时再沿 `[[笔记名]]` 展开（按名解析：`rg --files -g '<笔记名>.md' $DEV_BRAIN`）。
   - hub 和本项目记录之外，至少做一次全库的标题和正文检索（含 `knowledge/` 和其他项目），问题涉及的技术、工具、外部项目在别的项目里可能已有结论；之后再判断够不够。
   - 无命中不硬找，进入下一步。
3. **可信度**：`ok` 可作结论，仍以当前代码和现场为准；`draft`、`verify-needed` 和不带 `status` 的原料只当线索。
4. **接续**：`rg -l '^- 状态：(待做|进行中|已暂停|待你判断)' $DEV_BRAIN/projects/<id>/tasks` 查未完成的任务。`待做`、`已暂停` 可直接领取：把「执行者」改成自己、状态改为 `进行中`（同机不用提交；从另一台机器领取时提交并运行 `dev-brain-curator sync`，让别的机器看到已被领取）。`进行中` 且执行者不是自己，说明别人可能还在做，先问用户，不自行接管；`待你判断` 先请用户判断。
5. **同一话题接着用原任务**：要建记录前先看本项目 `tasks/` 里有没有同一话题（同一个讨论、同一个方案的下一轮）的任务。有就接着用：`完成` 的改回 `进行中`，在「过程」里追加这一轮，不另建目录；只有目标确实换了才新建，并在新记录里链接旧任务。
6. **对齐**：除小修和一问一答外，按下节把思路讲给用户并等确认；确认后再按「任务记录」新建，写清目标、范围、验收例子和结构影响，用到的笔记记入「用到的知识」。

## 动手前对齐

检索和只读调查做完后、第一次改动前（改业务代码、建任务记录、写产出物），先把思路讲给用户并等确认。小修、文案、低风险局部调整和一问一答不用。

对齐稿写在回复里，不写文件，详略与任务大小相称，通常一屏内：

- **目标与范围**：做什么，明确不做什么。
- **改动思路**：打算怎么做、为什么；考虑过的备选和取舍。
- **结构影响**：哪些模块、接口、数据所有权会变；依据的代码位置（`仓库名@commit:路径`）和笔记（路径 + `status`）。
- **验收方式**：用什么例子或检查证明做对了。
- **需要你定的点**：有关键取舍时给出推荐项和理由，一次问完，不逐条拉锯。

确认之后：

- 把确认的目标、范围、验收例子和结构影响写进任务记录，然后连续工作，不逐步索取确认。
- 只在三种情况回头再对齐：实际做法要偏离已确认的思路（结构、接口、范围有变）、原假设被证据推翻、出现新的关键取舍。其余照常推进。

不用重新对齐：

- 用户的请求已经给出具体做法（指明改哪个文件、用哪个方案等）。
- 用户说了「直接做」「不用确认」。
- 接续已对齐过的任务（见「开工」第 4 步），方向要变时才回头对齐。

## 任务记录

- 位置：`$DEV_BRAIN/projects/<id>/tasks/<YYYY-MM-DD>-<短主题>/<YYYY-MM-DD> <任务标题>.md`，模板 `_system/templates/task.md`。目录名用不含空格的短主题（中英文均可）；文件名与 H1 一致，全库唯一（wikilink 按名解析）。不属于现有项目时用一个新的项目 id，只建任务目录，hub 由 curator 补。
- 状态取 `待做`、`进行中`、`已暂停`（已交出，任何执行者可领取）、`待你判断`、`完成`，写在「当前状态」的 `- 状态：` 行，只写这五个值之一，补充说明另起一行，便于检索。会话停下而没提交的任务目录，curator 会在它两小时没有改动后自动补提交（`autosave:`）。
- 一个任务一份当前记录，详略与任务大小相称，小任务一屏写完，不适用的节删掉。正文写当前进度和重要过程；完整日志、补丁、报告、草稿放同目录的 `logs/`、`patches/`、`artifacts/` 并在记录中引用。采集有缺口就标明缺口，不用事后摘要冒充原始记录。
- 一份文档只留当前版：讨论稿、方案稿用固定文件名，每轮直接改这一份，不按 v1、v2、v3 另存；旧版靠 Git 历史找回，每轮改了什么、为什么在「过程」里记一行。确实要并排对比时，旧版移到 `artifacts/archive/`，文件开头写明「已被取代，见 …」。
- 提交点：收尾时；停下等用户判断（状态改为 `待你判断`）时；已完成的任务又改了内容时，改完即提交。过程中只写文件，换机器交接或跨机领取时提交并同步。会话中途中断时文件仍在磁盘上，同机接续不受影响。

## 产物

讨论、调研、梳理、学习和开发中产出的文档、图、报告都存进 dev-brain，不放在代码目录旁、`~/Documents/Codex/...` 之类的输出目录或临时目录。调用其他工具或 skill 时直接把输出路径指到 dev-brain。

- 画图默认用 answer-me-with-html skill（没装时在 Markdown 里写 Mermaid 代码块，存放位置相同）：写 Markdown 草稿，由 `am render` 生成单文件 HTML，渲染时用 `-o` 直接写进 dev-brain，加 `--no-open`。作为项目长期参考的图放 `projects/<id>/diagrams/<主题>.html`，只服务这次任务的图放任务目录 `artifacts/`。源稿嵌在页面里，改图用 `am patch` 或用同一路径重新渲染，不手改 HTML。需要可交互的大型架构图或用户点名时再用 archify（细则见 `rules.md`「画图」）。
- 报告、草稿、抓取的原料、实验输出放任务目录；要写成正式笔记的，在 handoff 里指过去，由 curator 查重、拆分、落位。
- 提交交付物和可编辑源（HTML、JSON 规格、Markdown、补丁）；可再生的中间产物（视觉校验截图、构建缓存）不提交，在记录里写生成命令。

## 交接（暂停、换会话、换模型、换机器）

按模板各节更新任务记录，每项只写一处（同机换会话或换模型不用提交）：

- 「当前状态」：状态改为 `已暂停`（交出后任何执行者可领取；自己稍后还会回来做也一样），写执行者、更新时间、可直接照做的下一步。执行者写 `<codex|claude>@<机器名>`，机器名取 `~/.config/dev-brain/machine` 的内容；文件不存在时请用户起一个短名写进去。不要用 `hostname`：有些隔离工具会改写它，同一台机器上不同 agent 看到的不一样。
- 「代码位置」：仓库路径、分支、`git -C <仓库> rev-parse HEAD`；未提交修改存为 `git -C <仓库> diff --binary HEAD --output=<任务目录>/patches/<短sha>-<HHMM>.patch`，未跟踪文件（`git -C <仓库> ls-files --others --exclude-standard`）一并保存或列明。
- 「过程」：关键决定、已排除的方向；「证据」：已做的检查及对应代码版本。
- 原生 session ID 可作附加线索，接续不能依赖它。

要到另一台机器接续时，提交任务目录后运行 `$DEV_BRAIN/_system/bin/dev-brain-curator sync`，看到 `sync: ok` 再结束。业务仓库没有远端时，在记录里写明换机器需要怎样把代码带过去。

## 收尾

1. 涉及代码时，对最终待交付的代码状态运行与变化相关、项目要求的检查；证据写进任务记录：代码版本（commit，或基线 commit + 补丁）、命令、结果、原始输出位置。检查后代码又变了，证据作废，重跑。业务代码是否提交按用户和仓库的习惯。
2. 在「用到的知识」里写明每条旧知识是帮上了忙、与现实冲突还是没用上，依据是什么，以及缺了什么。
3. 有长期价值的结论就发 handoff（见下节），没有就不发；入队 id 写进记录。
4. 状态改为 `完成`，提交整个任务目录（`git add -- <任务目录>`，含 `artifacts/`、`logs/`，不要只提交主记录）。要停下等用户判断时也一样：状态改为 `待你判断` 并提交，不让材料只留在本机。
5. 回复用户：结果、行为与结构变化（及与原计划的偏差）、证据、遗留问题，以及交给 curator 的内容。

## 捕获（handoff）

时机：形成带理由的决定、得到有效验证、遇到重要失败时；暂停和收尾时检查一遍有没有这类结论还没发。同一任务的材料可以攒到交接或收尾时合成一份；只有进度、没有新结论时不发。

值得长期保存的：稳定事实、带理由的决定、可复用的步骤、明确的失败条件、持续影响工作的用户偏好。临时进度只留在任务记录。

按 `_system/rules.md` 的「dev-brain handoff 模板」写，入队后继续工作，不等 curator：

```bash
$DEV_BRAIN/_system/bin/dev-brain-handoff <<'EOF'
dev-brain handoff
project: ...
EOF
```

- Windows 写法见「Windows（PowerShell）」。
- 输出 `queued: <id>` 即入队成功，把 id 记进任务记录。本机装了 curator 时会自动开始整理。
- `links_or_assets` 带上任务记录、草稿和图的路径；`feedback` 写旧知识的使用反馈和依据。
- 内容多的（例如一次梳理要拆成好几篇笔记）：草稿写在任务目录 `artifacts/`，`summary` 写要点，由 curator 拆分落位。

## 整理

会话不写正式笔记，整理只由 curator 做（规则见 `_system/curator-session.md`）。

- 用户要求立刻落库：入队后运行 `$DEV_BRAIN/_system/bin/dev-brain-curator run`，结束后把它的输出（处理了哪些 handoff、提交、同步结果）告诉用户。
- 看 curator 状态和最近一次结果：`$DEV_BRAIN/_system/bin/dev-brain-curator status`。
- 用户要修改规则、skill、模板或脚本本身时，直接改 `_system/` 下的文件。

## 同步

会话只在开工时 `pull --ff-only`。推送和 `pull --rebase` 由 curator 执行器在每次运行后和每小时兜底时完成；换机器接续前运行 `dev-brain-curator sync`。冲突处理见 `_system/rules.md`「同步」。
